# Serial deadlines under concurrent kernel work

> Historical record: applies to the revisions and profiles described below.
> See the [current documentation](../architecture/overview.md) and [history index](README.md).

This is the measurement slice preceding shorter kernel critical sections. It
tests the diagnostic IRQ byte pump while other tasks enter the current kernel.
The [runner](../../tools/test_signal_concurrency.py) preserves functional results
and a separate baud verdict, including failing timing baselines. It does not
change scheduling or signal delivery.

The subsequent [critical-section implementation](kernel-critical-sections.md)
uses this same runner for acceptance. The numbers below preserve the original
baseline rather than describing the current kernel.

## Recorded baseline

The [qualification record](../qualification/signals-concurrency.json) contains
ten observed 4,096-byte cases and ten identical uninstrumented replays. All
twenty executions pass the functional checks, including guards, cleanup and
OS/serial ownership restoration. All active-kernel workloads **fail the
125 kbaud timing target**; the compute controls pass. Fifty package/parser
tests and ten observer interrupt-mask self-tests also pass.

| Workload | Raw late refills | Raw worst refill | Optimized late refills | Optimized worst refill |
| --- | ---: | ---: | ---: | ---: |
| Compute control | 0/4,095 | 59.771 µs | 0/4,095 | 60.334 µs |
| Yield | 1,632/4,095 | 561.618 µs | 1,704/4,095 | 559.926 µs |
| Signal/Wait + peer Yield | 1,970/4,095 | 1,454.794 µs | 1,973/4,095 | 1,353.296 µs |
| Timed Sleep | 76/4,095 | 1,384.873 µs | 76/4,095 | 1,288.451 µs |
| Mixed | 2,002/4,095 | 1,450.283 µs | 1,998/4,095 | 1,320.028 µs |

The optimized mixed run measures a **1,306.495 µs** longest I=1 interval.
Before the final refill it completes 140 root Yields, 141 signal round trips,
140 peer replies, 76 timed sleeps and 120 replies to a blocked root. Individual
counters can differ at the boundary because an operation can begin before the
final refill and finish after it.

The next slice must shorten complete protected service and scheduling paths,
including Signal, selection and timed wake handling. Optimizing `DrainOne`
alone cannot address the separate Yield/Sleep failures shown here. These are
observed workload maxima, not global bounds. Eight-task and long-run acceptance
remain separate qualification work.

## Workload and acceptance

The [fixture](../../tests/programs/signals_concurrent.act) keeps four public tasks
live throughout the transfer:

- The root runs the selected workload.
- A completion worker binds the serial source and blocks in public `Wait(1)`.
  The IRQ pump writes the generated byte sequence and posts once at block end.
- A signal peer waits for requests, yields so the root can block, and replies
  with another signal. Requests and replies use bits 31 and 30.
- A sleeper repeatedly calls `Sleep(1)` when enabled.

Five workloads separate the sources of interference. `compute` keeps the peer
and sleeper parked and makes no task kernel calls during transmission. `yield`
adds root Yield calls; `signals` adds request/reply Signal and Wait with peer
Yield; `sleep` enables the timed sleeper; `mixed` combines all three. Startup
waits until all workers are parked before starting the pump. Shutdown wakes
the peer and sleeper, releases serial ownership and waits for task removal.
The stop flag and two stop signals use Forbid/Permit after the transfer, keeping
both targets live until notification is complete.

Progress counters increment only before the final refill for Yield, signal
round trips, replies, timed sleeps and replies to a blocked root. The runner
requires progress for each enabled operation, correct full-width signal
results, exactly one block-completion Wait, and all requested bytes. Passive
routine markers independently show which paths ran during transmission.

The hardware checks require the exact byte sequence, no SEROUT overwrite,
no missing/extra writes or ready events, divisor 14, and completion of the last
byte. The common execution runner checks stack/DP guards, domain ownership,
task cleanup, native return state and OS vectors. The new runner also checks
serial IRQ enable bits, VSEROR, CRITIC and SKCTL shadow restoration.

Each observed run replays the **same XEX** on the uninstrumented emulator.
Runtime snapshots, task/context records, counters and serial ownership must
match exactly. This fixture checks ordinary compiled call state and the common
native boundary; it does not replace the dedicated all-register/M/X tests.

## Measurement

The [machine profile](../../toolchain/altirra-signals-1m.json) is the pinned native
AltirraOS ROM, PAL, 8× CPU, fast ROM, 1 MiB and normal VBI with scoped CRITIC
during serial ownership. Divisor 14 yields **126,674.821 baud**, a
**78.942286 µs** refill deadline. Generic OS I/O and timer callbacks are outside
this experiment.

The separate [observer pin](../../toolchain/altirra-concurrency-observer.json) and
[patch](../../toolchain/patches/altirra-concurrency-observer.patch) retain hardware
SEROUT/ready timestamps and full-address instruction markers. They add passive
I-flag transition observations **between CPU emulator microstates**, including
ROM and native/emulation status restores. Instruction-only sampling is
insufficient: RTI can briefly enable IRQs and take another interrupt before an
I=0 instruction executes, incorrectly joining two masked intervals.

No guest instructions, cycles, policy or emulator execution semantics are
changed. Timestamps resolve eighths of a base cycle at 8×. This measures the
emulator's I flag, including elapsed NMI, ROM and DMA time; it is not a physical
hardware worst-case guarantee or a complete model of interrupt recognition.
The observer patch applies to the corrected emulator revision in its pin;
use the CMake options in the [emulator build record](../../toolchain/altirra-build.json).
It is a complete observer patch, not an addition to the older signal observer.

Intervals are clipped to the first SEROUT write through final-byte completion.
All intervals are retained in `masked.csv`, with PCs, opcode at entry, boundary
clipping, IRQ/NMI origin and routine entries inside the interval. `results.json`
keeps the longest ten and those overlapping the worst refill. Routine entries
identify a path through the kernel; the interval duration is not an exclusive
per-routine cost. `refills.csv` retains every ready-to-next-write latency and
inter-byte gap. A masked interval longer than a byte does not by itself prove a
miss: it may straddle a refill performed by that IRQ. Hardware byte deadlines
are the acceptance criterion.

Raw emulator logs stay under ignored `build/` directories because they contain
local bridge credentials. Published records contain only parsed evidence and
artifact hashes.

## Running the test

The default runs raw and optimized mixed workloads, each with an uninstrumented
replay. `status: pass` means functional and measurement integrity passed;
`timing_verdict` separately reports baud suitability. Use `--require-deadline`
for a future acceptance gate that exits unsuccessfully on any late refill or gap.

```sh
python3 tools/test_signal_concurrency.py --compiler-dir build/actionc
python3 tools/test_signal_concurrency.py --compiler-dir build/actionc \
  --workload compute --workload yield --workload signals --workload sleep \
  --workload mixed --count 4096 --output build/signals-concurrency-baseline
python3 tools/test_signal_concurrency.py --compiler-dir build/actionc \
  --require-deadline
```

The default observer directory is `build/altirra-concurrency-bridge`; the replay
uses `build/altirra-irq-bridge`. Both binaries and the ROM must match their pins.
Runs have bounded completion. The default 4,096 bytes is a baseline workload,
not long-run or eight-task qualification. The pump generates TX bytes; RAM
buffer transfer, RX, SIO protocol and DOS remain later work.

## Memory budget

Reserved bank-zero change is **0 bytes**, fixed, per task and diagnostic. The
fixture uses the existing near-image reservation and the pump's existing
diagnostic counter at `$2080`. Host-side tracing consumes no guest storage.
The four-task layout retains 1,856 bytes per public context and another 1,856
for idle, with 11,824 fixed Exec runtime bytes. Complete reservations remain
21,104 runtime / 21,696 loading bytes excluding OS ranges, or
57,968 runtime / 58,560 loading including them. Guards, alignment and unused
reserved capacity are included; no task stack or direct-page reservation grows.
